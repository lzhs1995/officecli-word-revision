# 按操作划分并发资源

版本：操作并发说明 2026-09-30；仅文档，不改变现役锁或执行器。

Word 排队不等于整项研究暂停。调度按实际冲突对象划分，而不是把所有工具放入一条队列。使用既有唯一协调者和原账本；API、后台计算与桌面焦点分别判断。

| 操作组合 | 当前边界 |
|---|---|
| 冻结 DOCX/PDF 的只读核验、独立输出目录的离线工作 | 可并行；不读取正在写入的中间版本 |
| 两个 Word 原生写入/导出，Word 与 Zotero 引文插入或刷新 | 仍互斥；同一 Word 应用、插件状态与模态窗口可冲突，换文件名不能消除冲突 |
| Word 原生与独立 NLM 网络请求 | broker 资源不同；仅在传输不抢焦点、来源已冻结、各自准入和终态可核的情况下做受控实测；不同资源获准不等于原生组合已验证 |
| Word 与 Zotero 独立 API 查询 | 无需把 API 查询等同于 Word 插件操作；并发稳定性仍绑定实际 API/库版本与数据快照，不修改刷新正在消费的条目 |
| 两个 NLM 查询 | 复用已验证的同账号两路入口：不同 notebook、新会话、独立流及一次预算登记；其他环境不能照搬容量 |
| 同一文档、同一引文条目或同一会话的依赖写入 | 按依赖顺序执行；独立输出才可能并发 |
| 桌面点击/切窗与任何需要可见观察的操作 | 由唯一桌面协调者安排短事务，不能以 API 可并发推出焦点可争用 |
| NLM 音频后台生成与其他工作 | 创建请求实际终态后释放本地窗口；后台生成不占满整个问答周期 |

## 验证与启用

1. 核已存在的能力证据和固定执行器，避免为了证明并发重复已成功的论文审查。历史两路 NLM 完成不证明 Word+NLM 或 Zotero API+Word 已通过。
2. 优先选本来就需要执行的两项任务。分别固定来源哈希、文档/会话身份、输出路径、请求ID和恢复边界。独立进程和输出缓冲不能共享可变当前文档。
3. 记录真实操作重叠时段，以及输出、字段、引用、保存/重开、原始响应终态和各自回收。两个 ACTIVE 租约或退出码0仅能证明准入/进程结果。
4. 同对象冲突、模态、一个分支失败、原流未决时，保留原状态并阻止受影响的新准入；不要停止不相关资源，不要粗暴终止另一条健康流。
5. 报告通过的具体组合、次数、失败与未测范围。先在私有后继入口验证，再由原协调者按安全边界采用；不原位改已固定的运行时。

已复核的历史 NLM 两路证据包含两个真实完整终态及51个同时 RECEIVING 样本。此结论不保证当前账号健康，不证明提速倍数，不授权第三路。隔离测试证明现有 broker 可同时授予 Word 与 NLM 两类资源，同时拒绝第二个 Word 写入者和第二个 NLM 组；它不调用真实 Word、Zotero 或 NLM。

公开经验不包含论文原文、账号标识和本机私有证据路径。原生跨工具实测尚未完成时必须保持这一标注，不能将文档发布称为功能启用。

## 并发前的离线依赖核查

动态导入工作器时，应同时复现其固定解释器、第三方依赖目录和工作器自身目录。用 `importlib` 按文件导入不会自动把该文件的父目录加入模块搜索路径；相邻流处理模块因此缺失，不能据此认定服务不可用或所有任务必须串行。

本次离线实测在加入原工作器目录后，模块导入及连续三次同步 HTTP/2 客户端构造、关闭均通过。连接调用被禁止，认证资料未加载，原执行器文件未修改。此结果仅覆盖导入和客户端构造；异步流、真实认证、在线请求和 Word 重叠执行仍须分别验证。原 owner 消费证据后修复自己的预检入口，不由旁路改写在途任务。

## 原生作业结束、成品接受与调度交接

一次四表实测已完成 Word 保存、关闭、重开、PDF 导出和关闭，共八页；逐页观察确认续页表头及系数/标准误成对。原版分页问题保留，独立阅读版只增加行不拆分、重复表头和段落跟随属性。原有 1,092 个单元、空白与表外文字均按源合同核同，最终清单的成品和证据字节再次核验。

这证明该批 Word 原生路线及归还闭环有效，不证明 Zotero 引文刷新或 Word 与 NLM 已同时运行。应分别保存三类结果：

- 作业终态与资源归还：原进程终态、文档关闭、集成状态和锁回执，供唯一协调者继续原队列。
- 成品接受：来源身份、内容合同、实际页面和输出哈希；离线复核不继续占用已经归还的 Word 资源。
- 消息交付：完成报告先落盘，回调绑定报告哈希及 nonce；消息入队、接收端消费和回执文件生成分别核实。接收端短暂未读到回执文件，不推定原生作业未结束，也不重发已入队回调。

原生后继使用最新已核候选的精确哈希。新候选只在尚未开始的安全边界替代旧候选；在途作业保持原身份，不能静默换输入。报告须注明是否由监督重新查看页面，还是消费原执行者的逐页证据。

## 实际时间线与 Zotero 验收范围（2026-09-30 补录）

一次真实组合任务中，Word 已保存并关闭，5.010293 秒后 NLM 才发出来源注册 POST；网络完整接收并归还，实际操作重叠为零。此例证明先后执行成功，不能作为 Word+NLM 并发通过证据，也不能把 `source_add` 当作长问答。历史双 NLM 的 19 项证据再次核对哈希，仍对应 51 个同时 RECEIVING 样本和两个 COMPLETE；没有为补录重新提交请求。

跨工具验收应使用同一时钟基准的真实操作区间，计算 `max(0, min(end_a, end_b) - max(start_a, start_b))`。需要区分进程启动、资源准入、Word 打开至关闭、网络 POST 至完整接收、远端请求终态。包装器同时存在、两个租约 ACTIVE 或 HTTP 200 都不能代替实际重叠与各自成品验收。下一次使用两项必要且相互独立的真实任务验证；来源若由本次 Word 输出产生，应先完成该依赖，不为制造重叠提前提交。

该阶段的 Zotero 保存文件中可核得 21 个引用域、38 次文献项目出现，宏调用返回。这仅为 `PASS_STRUCTURAL_ONLY`：既有域可能来自原文件，不能据域数量或保存成功推断 Refresh 已完成。原严格失败继续保留；在该阶段尚无已验证可复用的 Refresh 完成观察器或集成传输绑定。完整接受需要将本次插入/刷新请求、真实集成终态、保存后引文及书目变化和实际输出绑定起来，不能把“找到 port/socket”本身当作成功。后续持久化证据见下节，不追溯修改此阶段判定。

当前 Word+NLM 查询、独立 Zotero API+Word、Word+Stata 的实际重叠均未接受。上述待测范围不阻止独立离线任务继续，也不改变既有唯一协调者、原队列或运行中的固定入口。权限恢复继续沿已授权流程执行，不为验证故意制造权限故障。

## 后续 Refresh 持久化与 profile 故障（2026-10-01）

后续一项任务已取得 Refresh 执行和保存/重开证据：正文19个引文域、脚注3个引文域，合计22个，另有1个书目域、24条书目；原生显示与保存 XML 相符。此次输入已含新增引用和书目，因此证明的是本次执行及持久化，不能称为首次插入。两处 `issued` 年份为字符串、批准元数据为整数，严格验收仍失败，`product_acceptance=false`。不以显示相同放宽原合同，也不为补写经验重复 Refresh。

另一个工作器在应用启动前因写死错误 profile 失败，原请求并未提交 Refresh。独立后继从 `profiles.ini` 解析唯一 `Default=1` 项，离线构造、原生前及配置写入前核 profile 目录、配置文件 inode 和配置 SHA；缺失、歧义或身份替换在调用应用前停止。44项离线测试及真实主机离线构造通过，只证明这个前置故障已修复，不授予原生刷新、TCC 恢复或并发通过。该后继的符号链接拒绝规则属于它的固定合同，不能据此宣称所有合法自定义 profile 都不可用。

普通 Word 打开超时需要核当前文档、精确目标路径及原生对话框。Word 的文件访问授权与 Zotero→Word 的 Apple Events 授权分别诊断；`-1712` 本身不是 TCC 拒绝证据。恢复沿原 owner、原票据和既有授权处理，不重放终态未知的打开或刷新调用。


## 跨工作区交接不改变 Office 资源状态

协调消息必须绑定原执行者的 workspace/surface UUID。当前工作区查不到目标时，由协作工具从实际工作区树解析唯一目标并重新核身份；不能据此替换执行者、另建队列或重发原生作业。完整定位及部分投递恢复规则由[论文精炼助手协作指南](https://github.com/lzhs1995/thesis-refiner/blob/docs/operation-concurrency-20260930/references/collaboration-and-recovery.md)维护，具体实现归协作工具。

消息失败发生在粘贴前、完整粘贴后或提交后，处理方式不同。保留原 delivery ID 和阶段证据，通过原目标锁与 helper 结算；已完整粘贴的消息不重复粘贴。消息已提交、接收端已消费和 Office 作业终态分别记录。任何消息修复都不能替代 Word 文档、模态、集成状态与原作业的真实归还检查，也不能把原生已归还误记为仍在途。

客户端折叠输入须先核实对应版本的展开行为及原完整文本；仅有一次特定版本的展开恢复证据，不能泛化为重贴。精确条件见上述协作指南，不在 Office 执行器复制另一套投递逻辑。

## 文件管理任务的修订边界

数据来源归档与文稿修订分别受任务范围约束。新复现文件不同于历史采用版本时，先登记差异和采用状态；不得仅因差异存在就调用Word批量替换数值、改结论或重制配套成果。已经生成的独立候选保留，但不自动成为正式稿。

工具维护和并发实测单列交付状态，不自动让已冻结文稿进入新审轮。用户仍要求的验证继续保留待办；未测组合不能因文档发布而被宣布可用。总流程见[文件管理与采用边界](https://github.com/lzhs1995/thesis-refiner/blob/docs/operation-concurrency-20260930/references/file-management-scope.md)。

## 准入计时与原请求未决（2026-10-01 补录）

一次原作业在应用准入前exit3，Refresh未提交，进程组已终态；原票仍需满足原生归还条件。两次有界只读观察共16个样本，总HID空闲均不足0.5秒，固定门槛为8秒。普通键鼠空闲多分钟及系统记录中的触控板相关事件不能直接解释总计时重置原因，也不能证明未知文档占用或TCC故障。两次循环均结束，未调用Office或归还控制器，未持锁等待；不得替换计时指标、降低门槛或把进程终态代作归还证据。

协调记录应分别给出原调用是否提交、原进程终态、最后原生观察、准入条件及下一次最早核查时间。原条件满足后，由原owner或既有合法委托沿原票重新核身份、同inode锁及文档/模态/集成状态；不重放原作业。不因观察结束而新设重复轮询队列。

并行NLM分支在本地接收上限停止后，原查询远端终态仍未知；原status/history的HTTP 200与空结果不足以接受或释放原查询。执行会话的401/额度耗尽又是另一故障，不能解释为Word权限问题，也不授权换会话重发。完整网络与认证处置见[并发与恢复边界](https://github.com/lzhs1995/thesis-refiner/blob/docs/operation-concurrency-20260930/references/operation-concurrency.md)。

历史Word保存/重开/PDF和后续22引文域、1书目域、24条目的持久化证据保持原范围。上述新观察没有新增任务级Refresh、真实TCC恢复或Word+NLM重叠通过；文档补录不改变现役执行器与释放条件。
